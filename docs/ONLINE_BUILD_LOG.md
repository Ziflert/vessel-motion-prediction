## ШАГ 5 — finetune-контур (2026-09-28, ВЫПОЛНЕНО)

**Создано:**
- `run_training.py`: новый флаг `--init-from <run_dir>` — warm start весами из
  `checkpoints/best_model.pt` (это и есть «дообучение», не переобучение с нуля).
- `online/finetune.py` — полный контур (план §8):
  1. cooldown-проверка (`results/online/.finetune_state.json`, default 60 мин);
  2. извлечение error_anomaly-сегментов из session.csv (+контекст seq_len назад,
     слияние кусков) или всей сессии (--all-rows) → `data/online_finetune/*_ft.tsv`;
  3. min-объём (default 600 строк, план §7) — отказ с внятной причиной;
  4. дообучение: subprocess `run_training` с `--extra-train-csv` (базовые данные +
     уникальные сегменты, E3-путь), `--init-from` (warm start), LR = базовый × 0.3,
     max_epochs=20, patience=5, **wall-clock timeout** (subprocess.run(timeout));
  5. валидационный гейт: test MAE нового run <= базового × 1.02 на ТОМ ЖЕ
     фиксированном holdout (сравнимые manifest-метрики); провал →
     `status='rejected-finetune'` в manifest, cooldown не начинается;
  6. успех → candidate + cooldown; автосвитча нет (ADR-6).
- Отчёт сессии: `results/online/<id>_finetune/report.json`.

**Решение-отклонение (зафиксировано):** гейт по «сегментам сессии» из плана §8
НЕ делаем — новая модель дообучена на этих же строках, метрика вырождается
(leakage). Гейт — только честный holdout; в manifest пишутся оба числа.

   width=-8 в ШАГЕ 3) → создание ленивое при первом открытии вкладки.
4. Программный `setCursor` во время бегущей сессии бессмыслен (каждый tick
   перерисовывает) — тестировать наведение нужно на остановленной сессии,

## График «прогноз — прошлое» + устойчивость старта сессии (2026-09-28, запрос заказчика)

**Запрос:** на онлайн-графике видно только текущий прогноз (жёлтый, вперёд) и факт;
заказчик хочет, чтобы после наступления спрогнозированного момента история прогнозов
сохранялась — наглядная оценка качества «на графике, а не по цифрам». Также вопрос:
делает ли модель переоценку, когда видит, что ошибается (см. ответ ниже).

**Сделано (online/static/panel.js, v4):**
- WS-tick уже приходил с полным массивом `preds` [horizon × n_targets] — сервера не трогали;
- фронт хранит историю прогнозов `state.forecasts` (bounded HISTORY + 2×HORIZON);
- две новые серии на графике сессии:
  - «прогноз был (1 шаг назад)» — что модель говорила за секунду до факта (зелёная);
  - «прогноз был (20 шагов назад)» — прогноз на полную дистанцию горизонта (розовая, пунктир);
  - текущий «прогноз (сейчас)» — как раньше (жёлтый пунктир);
- смена цели/рестарт сбрасывают историю корректно.

**Устойчивость:** `/api/session/start` принимает `speed/time_scale = null`
(дефолт 1.0 вместо 422), `panel.js` страхует `parseFloat(...) || 1.0`.

**Приёмка (100×, smooth0 K=9, ~480 тиков):** серии заполнены (359 точек),
числовая сверка по Roll: «1 шаг назад» MAE 0.37° < «20 шагов назад» MAE 0.87° —
серии честно отражают деградацию прогноза с дистанцией.

**Ответ на вопрос о переоценке (зафиксирован в IDEAS.md C6):** НЕТ, в текущей версии
модель НЕ переоценивается при высокой ошибке. Контур такой:
- error_anomaly — только МАРКЕР оператору (ratio > 2.5× базовой MAE, гистерезис);
- адаптация — оффлайн-дообучение по экспортированным сегментам с валидационным гейтом
  и ручным выбором модели (ADR-6: автосвитча сознательно нет);
- авто-адаптация «в контуре» (rolling finetune / рекалибровка при дрейфе ошибки /
  доверительное переключение по MC-Dropout-интервалам) — в планах v1.1+ (IDEAS C6).

## ADR-1. Локальный веб-интерфейс: FastAPI + WebSocket + vanilla JS

**Контекст.** Нужен UI для 1 Гц-стриминга без деплоя наружу.

| Вариант | + | − |
|---|---|---|
| **FastAPI + uvicorn + WS + одна HTML-страница** | полный контроль tick-цикла; WebSocket — естественный push; bind `127.0.0.1` = безопасность; мало магии, легко отлаживать | больше boilerplate, чем у Streamlit (смягчено: один файл сервера + одна страница) |
| Streamlit | самый быстрый старт | модель реранов Streamlit воюет с 1 Гц-циклом; слабый контроль над таймингом и backpressure; стриминг-графики — костыли |
| Tkinter/PyQt (десктоп) | нет браузера | тяжело поддерживать графики реального времени; хуже переносимость; нечего давать в браузер |

**Решение:** FastAPI. UI отдельно от ядра (ШАГ 1–2 работают через CLI без UI).

## ADR-2. Графики: uPlot

| Вариант | + | − |
|---|---|---|
| **uPlot** | один маленький js-файл, создан для временных рядов (миллионы точек), canvas → низкая нагрузка | меньше «из коробки», tooltips вручную |
| Chart.js | простота | тяжелеет на длинных сериях 1 Гц |
| plotly.js | богатство | тяжёлый (~3 МБ), избыточен |

**Решение:** uPlot, зависимость кладётся в `online/static/vendor/` (офлайн).

## ADR-3. Детекция нетипичности: два независимых маркера

| Вариант | + | − |
|---|---|---|
| **Z-score входа по scaler-статистикам (принято, v1)** | бесплатно (mean/std уже в scalers модели), интерпретируемо, zero-shot | игнорирует корреляции признаков; статистики = mean/std глобальные, не per-regime |
| Mahalanobis по ковариации train | учитывает корреляции | требует пересчёта ковариации из train-CSV; чувствителен к вырожденности (Wave.direction ≡ const в записи!) |
| Автоэнкодер на входах | ловит сложные аномалии | новая модель = новая точка отказа, обучение, порог; избыточно для v1 |

**Решение:** v1 — z-score (порог z=4, конфиг); Mahalanobis — план v1.1.
**Маркер ошибки** (rolling MAE факт-vs-прогноз vs k×val-MAE) — отдельно:
вход-аномалия ≠ «модель ошибается», это разные сигналы оператору.

## ADR-4. «Память» = скользящее окно 120 строк, без персистентного состояния

Модель — Seq2Seq без скрытого состояния между прогнозами; LSTM держит контекст
внутри окна `sequence_length=120`. «Память» системы = RingBuffer. Персистентность
буфера между запусками — v1.1 (сериализация deque): меньше сущностей в v1,
прогрев сессии 2 мин — приемлемая цена.

## ADR-5. Маркер уникальности = устойчивый `error_anomaly`, не одиночный выброс

- **Уникальность оценивает сама модель** (у оригинального авторефера:
  «данные, которые не может предсказывать модель») → маркер ставится по
  **ошибке прогноза**, устойчивой во времени (2 подряд / 2 из 3 окон).
- `input_anomaly` (статистический выброс) — информативный маркер оператору,
  но НЕ критерий дообучения: выброс может быть поломкой датчика, и обучение на
  мусле запрещено (урок §6 RESEARCH_LOG про «мёртвые» сегменты E-1).
- Дообучение — только по явному решению человека (CLI), не автотриггер.

## ADR-6. Дообучение — оффлайн-процесс, из realtime-цикла изъят

- Realtime-контур лёгкий и предсказуемый; обучение (CPU, десятки минут) в нём
  же = блокировка прогноза, сложность потоков, риски для стабильности.
- Finetune = отдельный CLI со своим watchdog'ом; результат — новый run в
  реестре `candidate`; замена модели в UI — только вручную оператором после
  валидационного гейта. Автосвитч запрещён (v1): цена ошибки выше выгоды.

## ADR-7. Формат входа live-режима = raw-строки train-CSV (до инженерии)

Контракт: словарь «колонка → значение» той же схемы, что колонки
`data/raw/your_data.csv`; инженерию (sin/cos углов, относительный КУ волны)
система применяет сама той же `engineer_features_dataframe`, что при
обучении — по параметрам из manifest модели. Иначе расхождение признаков =
тихая порча прогноза.

## ADR-8. Приём данных к записи — безусловно, маркеры — колонками

Все live-строки пишутся в session-CSV всегда (данные дороже диска); маркеры
аномалий — отдельные булевы/флоат-колонки + события в events.log. Экспорт
на finetune — проекция session-CSV по маркерам. Не наоборот («писать только
аномалии») — теряется контекст и валидационный материал.

## ADR-9. (изменение ADR-3) ErrorMonitor срабатывает по MAX per-target ratio

**Контекст.** Приёмка ШАГА 4: при усреднении ratio по 8 целям сдвиг физики на
2–3 целях «тонул» — агрегат не доходил до порога (max 0.746 при вставках),
потому что базовый MAE сильно разнороден (Velocity.Rolling 71.6°/мин vs Pitch 0.4°).

**Решение:** `ratio_max = max_over_targets(err/baseline)`, срабатывание если
ratio_max > k. Уточнение v1.1 (план §11) перенесено вперёд — найдено эмпирически.
UI/CSV дополнительно пишут ratio_mean для контроля.

## ADR-10. Дизайн «уникальных вставок» в MockLiveSource

Уроки приёмки ШАГА 4 (все эмпирические, проверены прогонами):
1. **Ступенька руля ±25° НЕ делает данные уникальными** — она в диапазоне train
   (±35°), модель интерполирует (max ratio 0.46).
2. **Вставка короче окна (40 < 120) «впитывается»**: входы=цели в Seq2Seq,
   окно быстро наполняется новым режимом, модель адаптируется.
3. **Работает: сдвиг амплитуды качки ×motion_scale на ≥200 tick.**
   ×2 → ratio 2.25 (у порога 2.5); ×3 → маркеры уверенно (71/71 внутри вставок).
4. Естественные пики ошибки (манёвры) тоже дают маркеры — это корректное
   поведение детектора, не шум.

## ADR-11. Разделитель списков в CSV-колонках — ';'

`input_anomaly_features` писался через ','.join → запятые ломали колонки
session.csv (статус-счётчик 64, CSV-колонка пуста). Фикс: ';' в engine
(единая точка для CLI и сервера). Мораль: любые списки в CSV — через ';'.

## ADR-12. Пороги «не верить прогнозу» — эмпирические per-target, не номинальные z

Валидация N4 (`results/mc_dropout_n4/`, 2026-09-30): покрытие интервала ±1.96σ MC-Dropout
НИЖЕ номинала 95% почти везде (0.3–0.7; light Pitch 0.95 — исключение). При этом
упорядочивание правильное (std_mean растёт с тяжестью режима ×5–6) и corr(std, |error|)
+0.6…0.9 per-segment. Альтернативы: (а) номинальные z=1.96 → статусы «не верить» почти
никогда бы не срабатывали (ложная уверенность, противоположный отказ СППР); (б) пост-
калибровка (isotonic/conformal) — корректнее, но требует отдельной работы (связь с B2/F2.3).
Решение: эмпирические пороги per-target в физических единицах (uncertain_max_std),
значения из severe/light-квантилей оценки N4; пост-калибровка — будущее расширение.

## ADR-13. MC-сэмплы батчами (repeat_interleave), eval() перед основным прогнозом

Поштучный цикл predict_uncertain давал ~1–2 с на 30 сэмплов на CPU — сорвал бы ритм
tick-цикла (tick 1 Гц). Фикс: сэмплы батчами repeat_interleave — один forward на батч,
dropout-маски независимы на элемент батча (математика MC не меняется) → 124–159 мс.
Плюс защита: eval() перед каждым ОСНОВНЫМ прогнозом — зомби-поток stale-MC мог оставить
модель в train-режиме (dropout активен → деградация основного прогноза).

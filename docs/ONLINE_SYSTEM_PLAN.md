# 📡 ПЛАН: Онлайн-система прогноза (streaming inference + live-режим)

> **Статус: v1.0 (план, 2026-09-27).** Это рабочий документ этапа «онлайн-система».
> Решения с альтернативами и ± — см. `docs/ONLINE_DECISIONS.md` (ADR-журнал).
> Прогресс отмечается здесь в §10. Протокол чтения проекта — `CONTEXT.md`.
> **Замысел исследования — `CONCEPT.md` (онлайн-режим — §4.2).**

---

## 1. Цель и границы (scope)

**Цель.** Локальная система, в которой обученные LSTM-модели работают «в онлайне»:

- **Режим A (тестовый/симуляция):** загружаем дата-сет → значения передаются
  **раз в секунду** (1 Гц), как с датчиков → на каждом шаге отображается прогноз
  поведения судна на `n` шагов вперёд. Плюс: фактические значения накладываются
  на прогноз с задержкой (когда «будущее наступило») — видимая ошибка в онлайне.
- **Режим B (реальные сенсоры):** тот же формат строки, что в режиме A.
  Прогноз с учётом «памяти». Нетипичные данные → **маркер**. Все входные
  параметры **записываются в дата-сет**. Уникальные (для модели) данные →
  маркер → накопление → **дообучение** LSTM на уникальном.

**Не входит в scope (v1):** деплой на внешние серверы (только `127.0.0.1`),
интеграция с реальным железом (источник данных — абстракция + mock),
СППР/нечёткая логика, превентивный режим (§4.1 CONCEPT).

**Ключевая связка с исследованиями:** онлайн-детекция «нетипичности» — это
практическая реализация гипотезы покрытия Ω (CONCEPT §3): если текущее условие
не покрыто базой → модель обязана об этом сигнализировать.

## 2. Уточнение терминологии (важно, до кода)

- **«Память» модели = скользящее окно.** LSTM — Seq2Seq без скрытого состояния
  между прогнозами: «память» — это буфер последних `sequence_length=120` строк
  (2 мин при 1 Гц). Новая строка → сдвиг окна → новый прогноз. Персистентность
  между запусками сессии — опционально (сохранение буфера на диск).
- **«Нетипичные данные» (аномалия входа)** — статистический выброс относительно
  распределения train (пространство признаков). **«Уникальные данные»**
  (аномалия ошибки) — там, где модель систематически ошибается сильнее обычного
  (пространство выходов/поведения). Два разных маркера, два разных порога —
  не смешивать.
- **Горизонт `n`** — параметр UI (по умолчанию `prediction_horizon` модели = 20
  шагов = 20 с; модель trained на фиксированный горизонт, произвольный `n` в v1
  не поддерживается — только отсечение отображения первых `n` шагов).

## 3. Архитектура (v1)

```
┌───────────────────────────── online/ (новый пакет) ────────────────────────┐
│                                                                              │
│  sources.py   TestSource (CSV playback)      LiveSource (mock/интерфейс)     │
│      │                1 строка/сек, speed multiplier                        │
│      ▼                                                                       │
│  buffer.py   RingBuffer (deque maxlen=2×max(seq_len,600)) ── «память»       │
│      │              warm-up: <120 строк → статус «прогрев», прогноза нет    │
│      ▼                                                                       │
│  engine.py   PredictionEngine (обёртка VesselPredictor_Inference)            │
│      │              predict() / predict_uncertain() + WATCHDOG               │
│      ▼                                                                       │
│  anomaly.py  InputAnomalyDetector (z-score по scaler-статистикам train)     │
│      │       ErrorMonitor (rolling MAE факт-vs-прогноз, hysteresis)         │
│      ▼                                                                       │
│  recorder.py  режим B: append session-CSV (raw строки + маркеры +         │
│      │                     прогноз + факт + ошибки)                         │
│      ▼                                                                       │
│  server.py   FastAPI + WebSocket (bind 127.0.0.1) → JSON на каждом tick     │
│              + REST: /models, /datasets, /start, /stop, /config             │
│                                                                              │
│  static/index.html  UI (одна страница, vanilla JS + uPlot)                  │
│  finetune.py  ОФФЛАЙН: сбор размаркированных сегментов → дообучение (CLI)   │
└──────────────────────────────────────────────────────────────────────────┘
```

**Инвариант потока:** один планировщик-tick в секунду: `tick → строка → буфер →
(если буфер полон) прогноз+аномалия → broadcast → запись`. Никаких вложенных
циклов ожидания; каждый узел имеет таймаут и путь деградации (§7).

**Почему локальный веб (а не десктоп-GUI/Streamlit)** — см. ADR-1 в
`ONLINE_DECISIONS.md`.

## 4. Режим A — тестовый (CSV playback)

1. UI: выбор модели (из реестра `models_archive`, только модели с manifest),
   выбор CSV, скорость воспроизведения (1×, 5×, 20×, max), play/pause/stop,
   `n` (сколько шагов прогноза показывать).
2. Сервер читает CSV (sniffing формата как в `run_inference.py`: tab/utf-16),
   применяет **ту же инженерию признаков, что зафиксирована в manifest модели**
   (`engineer_features_dataframe`).
3. Tick каждую секунду (или быстрее при speed>1): строка попадает в буфер,
   после прогрева на каждом tick'е — прогноз на 20 шагов.
4. UI: график истории (оконная выборка последних ~600 точек) + прогнозная
   «лента» с областью; через `n` секунд фактическое значение накладывается на
   ранее сделанный прогноз (визуальная ошибка в реальном времени).
5. Маркеры аномалий — те же, что в режиме B (детектор общий).
6. Стоп: bounded — конец файла = конец сессии (никаких «wait» после EOF).

## 5. Режим B — реальные данные (live)

1. Источник — интерфейс `LiveSource.get_row() -> dict | None` (контракт: словарь
   ключей = колонки train-CSV в raw-виде, ДО инженерии признаков; 1 значение/с).
   Реализации: `MockLiveSource` (генератор/синтетика — для разработки) и
   заглушка `FileLiveSource` (те же CSV, но без знания будущего в UI).
2. Каждый tick: raw-строка → session-CSV (`data/online_sessions/<YYYYMMDD_HHMMSS>.csv`,
   raw-колонки + служебные: `is_input_anomaly`, `is_error_anomaly`, метрики).
   **Запись безусловная**, маркеры — отдельные колонки.
3. «Уникальные» данные = сегменты с устойчивым `error_anomaly` (не одиночный
   выброс): критерии → §7 ADR-5.
4. Кнопка/флаг «экспорт для дообучения» — из сессии извлекаются сегменты,
   размечённые как уникальные (+ ручная метка оператора, как в CONCEPT §2 —
   weak labeling), в формат train-CSV.
5. Дообучение — **только оффлайн-командой** `python -m online.finetune ...`,
   не в realtime-цикле (§8). Новая модель регистрируется в реестре как
   `candidate` со статусом `online-finetune`, исходная не трогается.

## 6. Детекция «нетипичных» данных (двухуровневая)

| Уровень | Что меряет | Метод (v1) | Маркер |
|---|---|---|---|
| Вход | похожесть текущего условия на train | робастный z-score по каждому признаку (mean/std из scaler модели; порог настраиваемый, по умолчанию z=4) | `input_anomaly` |
| Выход | поведение модели | rolling MAE(факт, прогноз) за последние 20–60 с vs порог = k×(val MAE модели из manifest) | `error_anomaly` |
| Опц. | неуверенность | MC-Dropout std (`predict_uncertain`), каденс 1 раз в 10 tick (дорого) | отображается лентой |

Анти-дребезг (hysteresis): маркер ставится/снимается по двум подряд (или 2 из 3)
срабатываниям; одиночные всплески логируются, но не меняют статус.

## 7. Ограничения, таймауты, защита от бесконечных циклов

| Узел | Ограничение | При превышении |
|---|---|---|
| Tick-планировщик | 1 tick/сек, привязка к стенным часам (дрейф недопустим: пропуски, а не догон) | — |
| Inference (1 вызов) | watchdog **5 с** | пропустить tick, счётчик stale; UI: «прогноз устарел» |
| 3 подряд stale | порог | пауза источника, красный баннер (модель жива, поток остановлен) |
| WS-отправка | таймаут 1 с, очередь ≤ 2 (backpressure: старые tick'и выбрасываются, UI по последнему) | деградация плавности, не паника |
| Playback | конец файла = конец; speed ∈ [1..100]; число строк файла — естественная граница | авто-stop |
| Live-сессия | максимальная длительность (конфиг, default 24 ч) + heartbeat-лог | авто-stop + отчёт |
| RingBuffer | `maxlen` фикс. (2× max(seq_len, 600)) | невозможно расти бесконечно |
| Дообучение (finetune.py) | min уникальных строк (default 600), max_epochs=20, patience=5, wall-clock лимит 30 мин, cooldown между запусками ≥ 1 ч | отказ с понятной причиной в лог |
| Model swap | только через валидационный гейт: новая модель ≥ базовой на её же holdout + на сессии | иначе кандидат не активируется |
| Аномалия | пороги из конфига, у каждой метки cooldown (не чаще 1 смены/10 c) | нет flapping |

Дополнительно: все значения таймаутов — в `config/online.py` (dataclass), не
вразброс по коду; любой таймаут логируется в сессионный лог (§9).

## 8. Дообучение на уникальных данных — контур (offline)

1. `python -m online.finetune --session <csv> --run-id <base> --out-notes "..."`.
2. Скрипт: читает session-CSV → сегменты с маркерами уникальности (или полные
   сессии по флагу) → формирует train-выборку (окна строятся той же
   `data/dataset.py`) → проверяет min-объём.
3. Обучение с watchdog'ами (§7), early stopping, фиксированный seed.
4. Валидационный гейт на holdout базовой модели + на сегментах сессии.
5. Регистрация через существующий `registry.py`: новая версия run, status
   `candidate`, notes `online-finetune from <base_run_id>, session <csv>`.
6. UI показывает обе модели в списке; оператор сам выбирает (автосвитча нет).

**Ограничение-инварианты:** инвариант загрузки CONCEPT §3 (сессия относится к
одному состоянию загрузки — поле в конфиге сессии, по умолчанию наследуется от
базовой модели); исходная research-выборка/тесты не смешиваются с онлайн-
материалом — finetune-модель помечается и в исследованиях не участвует.

## 9. Логирование и контекст для LLM-сессий

1. **Сессионный лог** каждая live/тест-сессия: `results/online/<session_id>/`
   (session.csv — данные+маркеры; events.log — таймауты, ошибки, смены статуса;
   config_snapshot.json — вся конфигурация запуска).
2. **Технический журнал системы** — `docs/ONLINE_BUILD_LOG.md`: по одному
   разделу на шаг (§10), фиксирует «что делали / что сломалось / что решили».
   Без него сессии LLM теряют контекст между прогонами.
3. **Решения** — `docs/ONLINE_DECISIONS.md` (ADR, append-only).
4. **Прогресс/waypoints** — §10 этого плана: при завершении шага отмечаю `[x]`
   + краткий вывод. Новая сессия читает §10 → сразу видит точку восстановления.
5. Крупные ошибки/находки дублируются краткой строкой в `RESEARCH_LOG.md` §6
   (единый накопитель «граблей» проекта).
6. Все логи — append-only; ничего не перезаписывать задним числом.

## 11. Риски и открытые вопросы

- **z-score по признакам игнорирует корреляции** (scaler даёт только mean/std).
  Улучшение на потом: Mahalanobis по ковариации, посчитанной из train-CSV.
- **Порог rolling-MAE в физическом смысле**: val MAE из manifest — агрегат
  по всем целям; per-target пороги (вес Roll критичен — §5.5 RESEARCH_LOG) —
  v1.1.
- **Дрейф сенсоров** (не «уникальность», а поломка датчика) — v1 не отличает;
  маркер `input_anomaly` покрывает оба случая, для оператора это «проверить».
- Real hardware: `LiveSource` — единственная точка расширения; формат строки
  зафиксировать контрактом (§5) в `docs/ONLINE_API.md` на шаге 4.

## 1. Цель: зачем нужны данные (научная постановка)

**УТОЧНЕНИЕ заказчика (2026-09-28, критично):** текущий дата-сет УЖЕ снят на тренажёре по
задуманной схеме: направление ветра и волнения задавались КОНСТАНТАМИ, а курс судна
постоянно менялся манёврами (вправо-влево) → **КУ (курсовой угол) волнения/ветра меняется
ЧЕРЕЗ КУРС СУДНА**; затем погодные условия менялись ступенчато, снова манёвры. Погода
применяется ОТНОСИТЕЛЬНО судна: важен не постоянный курс волны/ветра, а КУСОВОЙ УГОЛ —
под каким углом волна/ветер наваливается на ту или иную часть корпуса.

**Проверено переанализом (§5.7 RESEARCH_LOG, `scripts/analyze_course_design.py`):**
- КУ волнения в записи ЕСТЬ: std 116.9°, полный диапазон [−180;180] через курс
  (Wave.direction ≡ 180° — НЕ дефект, а дизайн); покрытие: лаговая 50 %, кормовая 18 %,
  встречная 4 %;
- **зависимость «условия → качка» ЕСТЬ**: по 49 ступеням погодных состояний
  corr(std Roll, h_s)=+0.56, corr(std Pitch, h_s)=+0.74, corr(std Vertical, h_s)=+0.68 —
  правильная мера (амплитуда по состояниям), а не мгновенная corr ≈ 0 (обманывала:
  фаза осцилляций доминирует);
- КУ сигнал умеренный: corr(std Roll, доля лагового КУ)=+0.33;
- контур «руль→ROT→курс» ЧЕСТНЫЙ: corr(ROT, скорость изменения курса)=+0.985;
- канал Wind.speed в CSV НЕТ (только Wind.Force* эффекты) — добавить при сборе.

**Что модель уже видит:** признак относительного угла (Wave.direction − Course, sin/cos)
включён в вход (`relative_wave_angle=True`) — архитектура ПРАВИЛЬНАЯ, менять не нужно;
ошибка была в интерпретации, а не в коде.

**Цель сбора:** пополнить базу УПРАВЛЯЕМО покрываемыми состояниями Ω = {h_s, T_w, КУ,
сила/направление ветра, V судна} по СХЕМЕ ЗАКАЗЧИКА (фиксированная погода + манёвры
курсом покрывают все КУ бесплатно) — чтобы модель (1) устойчиво выучила зависимость
«условия × КУ → поведение судна» (по всем погодным состояниям, а не только в частотных),
(2) работала в превентивном режиме (CONCEPT §4.1), (3) дала domain randomization
для переноса на реальную запись.

### 2.2 Ключевые механизмы (то, на чём строится сбор)

1. **Diagrams → Export Diagram Data to CSV** (Instructor Manual, гл. 3/4, «Ship Diagram Window»,
   «Selecting Monitored Parameters», «Export Diagram Data to CSV-Format»):
   в окне Diagrams инструктор выбирает контролируемые параметры судна, видит их графики
   в ходе сессии И при воспроизведении лог-файла, и экспортирует данные в CSV
   с настройками **периода (Start/End) и шага (Step)** — выставить шаг 1 с.
   Это основной путь получения нашей таблицы «датчики 1 Гц».
2. **Markpoints on the Diagram** («Setting Markpoints on the Diagram», p. 180): инструктор
   ставит маркер (время + имя) на график в нужный момент — штатный механизм для
   **маркеров режимов волнения** (weak labeling, CONCEPT §2.4).
3. **Log-файлы (*.ntlog)** — хранятся в `NTPro…\LogFiles\<район>\`; содержат всю запись
   упражнения для playback; комментарии (судно, имя обучаемого, объект). Можно вернуться
   к лог-файлу позже и экспортировать CSV из playback (не только в момент сессии).
4. **NMEA Interface** (модуль NTPRO): генератор NMEA-сообщений, user-adjustable output
   sentences (Gyro, Log, Echosounder, ARPA и т.д.) → дополнительное ПО/оборудование
   через COM-порт/сеть — альтернативный путь записи на 1 Гц внешним логгером.
5. **Environment Settings** (EDIT\ENVIRONMENT SETTINGS): задаются ветер (узлы), высота волны
   (м), видимость; предустановленные типы погоды от Calm (force 0, 0.1 м) до Gale
   (force 8, ~3.5 м+); направление ветра и волнения; Overall Condition Manager;
   **динамическое изменение условий в ходе сессии** с пульта инструктора.
6. **Библиотека моделей судов** — различные корпуса/размеры; выбор модели = выбор судна
   для серии сценариев (инвариант «судно × загрузка», L-6).

## 3. Какие данные собирать (целевой формат)

**Формат:** та же структура, что у текущей `data/raw/your_data.csv` (TSV/UTF-16, 1 Гц),
чтобы пайплайн обучения работал без переработки. Обязательно ПОЛНЫЙ набор каналов:

| Группа | Каналы | Приоритет |
|---|---|---|
| **Качка** | Pitch, Roll, Vertical + 3 скорости (Pitching/Rolling/Vertical) | ★★★ цели |
| **Волнение (настоящее!)** | значительная высота h_s, **период T_w**, направление волнения, зыбь (высота/направление) | ★★★ — закрывает L-3 |
| **Ветер** | направление, скорость (уз) | ★★★ |
| **Течение** | направление, скорость | ★★ |
| **Управление** | Rudder Order, Rudder State, RPM | ★★★ (контур руль→ROT) |
| **Навигация** | SOG, STW, ROT, Course, Long, Lat | ★★ |
| **Моменты/силы** | Moment/Force (Yawing/Rolling/Pitching), Wind.* | ★ (опционально, для анализа) |

**Критические требования к качеству записи:**
1. **Настоящие параметры волнения** (h_s значительная, T_w, направление) — не сценарный
   индекс. Если симулятор экспортирует только заданные параметры сценария — фиксировать их
   в manifest и считать «заданными условиями» (это уже лучше, чем сейчас).
2. **Непрерывность записи 1 Гц** без пауз; БЕЗ «мёртвых» участков (стоянка до начала
   движения — урок E-1: val MAE 688σ на данных без сигнала).
3. Согласованность времени (UTC) между каналами; единый шаг (Step=1 с).
4. Единицы измерения выставить ДО старта (Settings/Units) и записать в manifest
   (градусы/метры/узлы — сверить с текущей записью).

## 4. Сетка сценариев — ЭФФЕКТИВНАЯ СХЕМА (v1.1: по заказчику; не тратить 40 ч вместо 8)

> Ключевая идея эффективности: **КУ покрывается МАНЁВРАМИ КУРСА при фиксированной погоде**
> (как и делал заказчик: повороты вправо-влево покрывают все КУ 0–360° автоматически).
> Менять направление волны в Environment Settings для каждого сценария НЕ нужно —
> это схлопывает сетку 5×2×5=50 сценариев до **10 погодных состояний × манёвры**.

**Инвариант (L-6 / CONCEPT §3 v1.1):** одна серия = одно судно × одна загрузка.
Загрузку в сетку НЕ включать — для каждого состояния загрузки отдельная серия и отдельная
модель (M_loaded, M_ballast). Записи разных судов не смешивать.

**Сетка по погодным состояниям (на одну загрузку):**

| № | Погода (Environment Settings, задать ДО старта) | Что покрывается манёврами | Время |
|---|---|---|---|
| 1 | штиль/лёгкая (h_s ≈ 0.5 м, force ~2) | все КУ манёврами | ~10 мин |
| 2 | умеренная (h_s ≈ 1.5–2 м, force ~4) | все КУ манёврами | ~10 мин |
| 3–4 | существенная (h_s 2.5–3.5 м) × 2 периода T_w | все КУ манёврами | ~20 мин |
| 5–6 | сильная (h_s 4–5 м) × 2 периода | все КУ манёврами | ~20 мин |
| 7–10 | опционально: штормовая (h_s 5–6 м) + изменение скорости | КУ × скорость | ~20 мин |

**Итого ≈ 80–100 мин на одну загрузку** (~5–6 тыс. строк при 1 Гц) — сопоставимо
с текущей записью, но с ПОЛНЫМ и управляемым покрытием Ω. Для 2 загрузок ≈ 3 ч.

**Инструкция записи одного погодного состояния (цикл, по заказчику):**
1. Задать погоду в Environment Settings (h_s, T_w, ветер константами, течение) — до старта.
2. Выполнить НЕСКОЛЬКО ПОЛНЫХ ЦИКЛОВ КУРСА вправо-влево (каждый цикл ~3–5 мин,
   покрывает все КУ 0–360°): 2–3 полных циркуляции на состояние — этого достаточно:
   по текущей записи КУ уже покрыт на 50 % (лаговая), манёвры добавят встречную (4 %)
   и кормовую равномерно.
3. **Маркер режима** (markpoint в Diagrams): время + имя `W_<h_s>_<T_w>` при задании погоды.
4. Смена погодных условий динамически с пульта инструктора (документировано §2.2.5) —
   запись НЕ прерывать; следующая ступень — новый маркер.
5. В конце серии — стационарный участок без манёвров (только качка, ~5 мин) —
   чистая точка «состояние без управления» (сравнение с манёвренными участками).

**Дополнительно (бесплатные бонусы той же схемы):**
- варьировать скорость в манёврах (ход полный/средний) — покрывает частоту встречи;
- один-два сценария с изменением НАПРАВЛЕНИЯ волны (Environment Settings) — проверка
  симметрии зависимости от КУ (не обязательно для основного объёма);
- один сегмент БЕЗ манёвров на каждом состоянии — чистая стационарная качка.

**Объём:** ориентир из E2/E3 — ~30 000 строк (≈ 8 ч) симуляторных данных + 1–2 ч реальной
записи — рабочая точка. Схема выше даёт ~1.5–2 ч на загрузку; для 30k нужно ~4–6 серий
(или добавить повторные циркуляции/длительность стационара). Рабочий минимум: 10 состояний
× манёвры ≈ 1.5 ч — уже рабочий набор для проверки зависимости по всем КУ.

## 5. Формат маркеров режимов (weak labeling судоводителем)

- Маркер = markpoint в Diagrams: `time` + `name`. Протокол имён:
  `W_<h_s>_<T_w>_<КУ>` (например `W_2.5_10_90`) — машиночитаемо для стратификации
  и метрики покрытия Ω.
- Дополнительно: комментарий к log-файлу (судно, загрузка, сценарий) — хранится
  вместе с *.ntlog (документация §2.2.3).
- После сбора маркеры переносятся в отдельный CSV-канал `mode_label`
  (как задумано в CONCEPT §2 — «судоводитель вносит маркер в дата-сет»).

## 6. Метаданные прогона (manifest сценария)

Для каждого упражнения (log-файла) фиксировать:
- имя упражнения, дата/время, версия симулятора, тип судна/модель, состояние загрузки;
- заданные условия: h_s, T_w, КУ волнения, ветер (направление/сила), течение;
- время начала/конца стационарного участка; шаг записи; единицы измерения;
- список маркеров (время → режим); комментарии инструктора.
→ пригодится для стратифицированной оценки и метрики покрытия Ω (G2).

## 7. Механика экспорта (после сбора)

1. **Основной путь:** Diagrams → выбор контролируемых параметров → Export Diagram Data
   to CSV (Start/End = границы стационарного участка, Step = 1 с) — отдельно на каждый
   сегмент; сшивка в один TSV нашим форматом (`load_data`).
2. **Альтернатива A (NMEA):** внешняя программа-логгер на COM-порту, собирающая
   user-adjustable NMEA-предложения на 1 Гц (Gyro → Roll/Pitch/Heading, Log → SOG,
   Echosounder → глубина) — если CSV-экспорт неудобен или нужен непрерывный поток.
3. **Альтернатива B:** playback log-файла (*.ntlog) → повторный CSV-экспорт из Diagrams
   (запись можно вернуться и экспортировать позже) — если в момент сессии экспортировать
   не удалось; параметры/шаг те же.
4. После сшивки — проверка целостности (скрипт по образцу `scripts/analyze_real_data.py`):
   std целей, наличие сигнала, corr(качки, условия) — зависимость должна ПРОЯВИТЬСЯ
   (corr(h_s→Roll), corr(T_w→период качки), corr(КУ→асимметрия)).

## 8. Валидация после сбора (критерий успеха)

1. **Проверка зависимости:** corr(h_s → амплитуда качки) существенно ≠ 0 по сетке
   (на текущей записи = 0.00 — вырождено); спектральные пики периодов качки согласованы
   с T_w сцены; зависимость от КУ (минимум на попутной, максимум на встречной/лаговой).
2. Повторить E1/E3 с «симулятор → реальность»: domain gap, перенос качки и ROT/SOG
   (у симулятора контур управления честный — ожидание: ROT/SOG переносятся, в отличие
   от статистического генератора G-3).
3. Обучение на симуляторных данных: learning curve MAE(n) на сетке; сравнение с
   генераторной синтетикой (§5.2/§5.3 лога: R² 0.63–0.67 — симулятор должен дать ≥).
4. Схема «много симулятора + немного реального» → дообучение/смешение → оценка
   на реальном тесте (E3-схема, domain randomization).

## 9. Риски и оговорки

- **Модель движения Transas ≠ реальный корпус**: перенос «симулятор → реальная запись»
  требует domain gap-оценки (E3-схема); симуляция обязана соответствовать категории
  «судно × загрузка» реальной записи (L-6), иначе аугментация теряет прирост.
- **Трактовка зависит от дизайна:** зависимость мерить АМПЛИТУДОЙ ПО СОСТОЯНИЯМ
  (corr(std Roll, h_s)), не мгновенной corr — урок §5.7 (мгновенная corr ≈ 0 обманывала
  на текущей записи из-за фазы осцилляций).
- **Канал Wind.speed обязателен**: в текущей записи его нет (только Wind.Force* эффекты) —
  запросить явно (узлы) при экспорте; без него зависимость «ветер → качка» не проверяется.
- Лицензионные опции (Record/Playback, NMEA Interface) могут отсутствовать в конкретном
  центре — чек-лист §2.3 обязателен до поездки.
- Доступ к симулятору — внешний блокер (учебный центр); сессия планируется по согласованию.

# 🔌 ONLINE_API — контракт live-источника данных (режим B)

> ШАГ 4 плана `docs/ONLINE_SYSTEM_PLAN.md`. Решение о формате — ADR-7
> (`docs/ONLINE_DECISIONS.md`). Для подключения реальных сенсоров реализовать
> `LiveSource` из `online/sources.py` по этому контракту.

---

## 1. Контракт строки (raw)

Источник выдаёт **RAW-строку** — словарь «имя колонки → значение» той же схемы,
что колонки `data/raw/your_data.csv` (TSV), **ДО инженерии признаков**:

- качка: `Pitch(градусы)`, `Roll(градусы)`, `Vertical(Метр)`,
  `Velocity.Pitching(°/мин)`, `Velocity.Rolling(°/мин)`, `Velocity.Vertical(узлы)`;
- навигация: `SOG(узлы)`, `ROT(°/мин)`, `Course(градусы)`;
- управление: `Rudder Order(градусы)`, `Rudder State(градусы)`, `RPM(Обороты в минуту)`;
- внешние условия: `Swell(метры)`, `Wave.Highest(метры)`, `Wave.direction(градусы)`,
  `Wave.speed(узлы)`, `Wind.direction(градусы)`, `Current.direction(градусы)`,
  `Current.speed(узлы)`;
- допустим колонка `time` (будет отброшена) и лишние колонки (игнорируются).

**Инженерию признаков (sin/cos углов, относительный КУ волны) применяет сама
система** — той же `engineer_features_dataframe`, что при обучении, с параметрами
из manifest модели. Источник инженерию НЕ делает (иначе расхождение = тихая
порча прогноза).

Требования к значениям: числа (или строки, парсимые как числа); NaN допустим,
но tick с NaN-окном пропускается прогнозом (событие в events.log).

## 2. Контракт ритма

- Ровно **1 строка в секунду** (1 Гц). Источник не должен «догонять» пропуски
  пачкой — система сама пропускает tick'и при отставании (дрейф недопустим).
- Блокировка `get_row()` — не дольше `timeout_s`; `None` = данных нет
  (tick пропускается, статус — в events.log).

## 3. Интерфейс реализации (Python)

```python
from online.sources import LiveSource

class MySensorSource(LiveSource):
    def get_row(self, timeout_s: float = 1.0) -> dict | None:
        # читать из сокета/файла/шины с таймаутом timeout_s
        ...
        return row  # или None
```

Подключение: добавить реализацию в `online/sources.py` и выбор в
`POST /api/session/start` (`source: "live"`) + `online/server.py`
(сейчас доступен `source: "live"` = `MockLiveSource`; точка расширения
помечена комментарием).

## 4. Что система делает с каждой строкой (режим B)

1. **Безусловно записывает** в `results/online/<id>_live/session.csv`
   (raw-колонки + `tick`, `predicted`, маркеры — ADR-8: данные дороже диска).
2. Прогноз через буфер-окно 120 строк (прогрев 2 мин).
3. Маркеры: `input_anomaly` (вход вне train-распределения) и `error_anomaly`
   (модель устойчиво ошибается) — план §6.
4. Сегменты с `error_anomaly` — кандидаты на дообучение (ШАГ 5, только
   по явной команде оператора).

## 5. Ограничения (план §7)

| Параметр | Значение |
|---|---|
| `time_scale` | 1.0 в эксплуатации (>1 — только dev/приёмка) |
| Лимит длительности | `max_session_hours` (конфиг, default 24 ч) или `duration_s` запроса |
| Пауза/стоп | `POST /api/session/pause`, `/api/session/stop` |
| Запись при закрытом UI | продолжается (серверная) |

## 6. Тестовые источники (уже реализованы)

- `MockLiveSource` — сидированный генератор: циклический проход по реальному CSV
  с сид-зависимого старта + опциональные «уникальные вставки» (ступенька руля
  ±25° — детерминированные сегменты, на которых модель должна ошибаться).
  Один seed → воспроизводимая последовательность строк и маркеров.
- `FileLiveSource` — CSV как «сенсор» (без знания будущего в UI).
